1. Overview & purpose

VMP (V MAX Protocol) is a custom application-layer protocol carrying telemetry and control traffic for a simulated agricultural IoT sensor network. Sensor nodes distributed across farm plots connect to one central server over TCP and operate in a hybrid model: nodes push readings to the server on their own schedule, and the server can push commands back to any node over that same connection at any time — there is no separate polling channel and no message broker.

Three node types are modeled, each measuring a different physical quantity:

TempHumidNode
Air temperature (°C) + relative humidity (%), paired — modeled on a DHT22-class sensor.
SoilNode
Soil pH and soil moisture (%).
LightNode
Light intensity, in lux.

A node's lifecycle is: connect → REGISTER → periodic PUSH (and an occasional self-check STATUS) → respond to any COMMAND the server sends → UNREGISTER on a clean shutdown. Every message either side sends or receives is printed to the console with its full status code and phrase, per the assignment's logging requirement.

2. Why TCP, not UDP

IoT telemetry commonly favors UDP for its lower overhead, and a TCP+UDP hybrid (UDP for node→server readings, TCP for server→node commands) was considered. VMP instead uses TCP for the entire system, for three reasons:

  1. The assignment requires printing the status code/phrase of every message sent and received. TCP guarantees in-order, complete delivery, so what gets logged always matches what actually happened on the wire. UDP packet loss would make that log misleading without extra bookkeeping.
  2. Server→node commands (e.g. "increase push frequency") need reliable delivery — a lost UDP datagram would leave a node silently misconfigured.
  3. Sensor readings inform real irrigation/fertilization decisions in the domain being modeled; losing them silently is undesirable.

The TCP+UDP hybrid was rejected because it would double the socket-handling logic (two transport types to manage per node) for a benefit — lower overhead — that matters far less at this system's scale than the risk of a status/data mismatch in the required logs.

3. Message format

Every VMP message is text-based: an HTTP-inspired start line, followed by Key: Value headers, a blank line, and a JSON body whose exact byte length is declared by a Content-Length header. This mirrors HTTP/1.1 framing directly — material already covered in the course — rather than inventing a bespoke binary layout.

Two design choices back this format:

  • JSON body, not a binary struct — the three node types carry different fields (temperature+humidity vs. pH+moisture vs. lux). JSON lets each type send its own shape without touching the header format. It is also directly human-readable in the terminal log the assignment requires, and needs no hand-rolled byte-offset parsing.
  • Content-Length framing, not newline-delimited JSON — TCP is a byte stream with no built-in message boundaries. Delimiting messages by \n risks corruption if a JSON value ever contains a literal newline. Declaring the body's exact byte length up front (as HTTP does) removes that ambiguity entirely: the receiver reads headers until a blank line, reads exactly Content-Length bytes of body, and is done — no scanning for a delimiter inside untrusted content.

Responses use the same shape, with an HTTP-style status line in place of the method line:

VMP/1.0 200 OK
Content-Length: 40

{"message":"Push received successfully"}

4. Concurrency model

The server must hold many nodes' connections open simultaneously — each REGISTERed node keeps its socket alive so the server can push a COMMAND to it at any later time — without one slow or idle connection blocking any other. VMP's reference server relies on Node.js's own event-driven, single-threaded I/O model rather than spawning one thread per connection: each incoming connection yields its own socket object via server.on('connection', ...), and every REGISTERed node's identity is mapped to that socket in a server-side connection table (Map<Node-ID, RegisteredNode>), so the server can look up any node's live socket later to deliver a COMMAND. This is idiomatic for the runtime, requires no manual thread lifecycle management, and Node's event loop already multiplexes the concurrent, I/O-bound socket traffic this workload consists of.

5. Methods

VMP defines five methods. REGISTER, PUSH, and STATUS are node→server; COMMAND is server→node; UNREGISTER is node→server.

5.1 REGISTER — introduce a node

Sent once, immediately after connecting, before any PUSH is allowed. Carries Node-ID, Node-Type, and Plot-ID, and optionally an Auth-Token (§8). A successful REGISTER binds the node's identity to this TCP connection in the server's connection table for the lifetime of the socket.

5.2 PUSH — report a reading

Sent periodically, node-initiated, carrying a Seq header (§7) and a JSON body shaped by the node's type. Only accepted for a node that has already REGISTERed on this connection.

5.3 COMMAND — instruct a node

Server-initiated, sent over the node's existing REGISTERed connection. Five subtypes:

SubtypeEffectPayload
SET_INTERVALChange how often the node pushes readings.{"seconds": n}
REPORT_NOWAsk the node to push its latest reading immediately, out of cycle.{}
SET_THRESHOLDAsk the node to push early whenever a given field crosses a minimum (e.g. soil moisture too low).{"field": s, "min": n}
CALIBRATEAdjust the node's sensor reading offset.{"offset": n}
SHUTDOWNTell the node to UNREGISTER and disconnect.{}

An operator REPL on the server lets a human send any of these interactively, targeting either a single Node-ID or an entire Plot-ID (§10).

5.4 STATUS — self-check

Empty-bodied request carrying only Node-ID; the server answers whether that node is still present in its connection table (200 + {"registered":true}) or not (401). The reference client sends one automatically every 3rd PUSH as a lightweight self-check, piggybacked on the existing push cadence rather than a new timer.

5.5 UNREGISTER — leave cleanly

Empty-bodied, node-initiated. The server removes the node from its connection table, answers 200, and closes the socket. Sent on an intentional disconnect (Ctrl+C, or a SHUTDOWN command) — never on an unintentional one, which the server instead detects via the socket's own close/error event.

7. Reliability: Seq & auto-reconnect ADR 0006 / 0007

TCP guarantees ordered, complete delivery within one connection — not across a reconnect. If a node's connection drops and it reconnects, the new connection has no memory of the old one; any reading in flight during the drop is simply gone, and neither side would otherwise know. Two features address this directly:

  • Seq header — an integer on every PUSH, starting at 1 and resetting to 1 on every fresh REGISTER (including after a reconnect). The server tracks the last Seq it saw per node; a jump ahead logs a likely gap, a repeat or a value at/below the last one logs a duplicate. This is detection and logging, not a retransmission layer — the server still processes and answers 200 regardless, deliberately staying inside the scope of what this assignment's logging requirement calls for.
  • Auto-reconnect with exponential backoff — an unintentional disconnect (socket close/error, as opposed to a deliberate UNREGISTER) no longer exits the client process. It retries the connection at 1s, 2s, 4s, 8s… up to a cap, resetting back to 1s once REGISTER succeeds again — realistic for a field sensor recovering from a transient network blip, and it avoids a reconnect storm if the server is down for a while.
  • SIGINT / SHUTDOWN are treated as intentional: the client marks the disconnect as intentional and sends UNREGISTER first, so the reconnect logic never fires for a deliberate exit.
Because both sides reset their sequence counters together on every fresh REGISTER, a genuine mid-stream gap cannot occur under normal operation — the detector's real job is catching a malformed or adversarial client, the same category as version validation (§9). This is a property of the design, not a bug: any anomaly detector is only exercised by deliberately bad input.

8. Authentication ADR 0008

By default VMP has no authentication — any client sending a well-formed REGISTER is accepted. An optional shared-secret layer closes that gap without requiring certificate management: the server may be started with --secret <token>; when set, REGISTER must carry a matching Auth-Token header or the server answers 403 Forbidden. Omitting --secret disables the check entirely, keeping the protocol backward-compatible with an unsecured deployment. Full TLS was considered and deliberately deferred (§13) — it would add real confidentiality, but at the cost of certificate/key setup that is a poor risk trade against the time remaining for the other two deliverables.

9. Version negotiation ADR 0009

Every start line has always carried a version token (VMP/1.0), but it went unchecked — any client, regardless of what it sent, was processed identically. The server now validates it on every request, before dispatch: a mismatch is rejected with 400 BadRequest rather than being parsed as if it matched. This turns the HTTP-inspired version token from decoration into an actual compatibility gate, and gives a future VMP/2.0 wire-format change a clean way to reject an incompatible older client instead of failing unpredictably mid-parse.

10. Group addressing ADR 0010

A single plot commonly hosts multiple node types that need the same instruction at once (e.g. "before the storm, every node in PLOT-01 should push more frequently"). The operator REPL's command <target> … accepts either a Node-ID (unchanged behavior) or a Plot-ID, which fans the same COMMAND out to every node currently registered in that plot — logged once per node, so the assignment's per-message logging requirement still holds for each individual delivery. This reaches the same practical outcome as MQTT's topic-based group addressing (§12), without introducing a broker: the server already tracks each node's Plot-ID in its connection table.

12. Comparison with MQTT / CoAP ADR 0011

VMP is not a bid to replace MQTT or CoAP in production — it is purpose-built for this assignment's specific constraints (hybrid push+command on one TCP connection, mandatory human-readable per-message logging, three node types with different fields). MQTT and CoAP are still the most relevant comparison points, since both target the same problem — sensor telemetry to a central point, with control flowing back.

AxisVMPMQTTCoAP

Schema flexibilityJSON body shape varies freely per node typeOpaque payload — schema is an application-layer conventionOpaque payload — same as MQTT

FootprintHeaviest of the three — JSON + text headersSmall, built for constrained/battery devicesSmallest — designed for 6LoWPAN-class devices

Where VMP trades away efficiency, it does so deliberately. The assignment requires printing every message and status code in human-readable form; a binary protocol would need a decoder written purely to satisfy that logging requirement, with no other benefit at this scale. The system also has no need for MQTT's broker (a handful of simulated nodes on one machine, not a large decoupled deployment) or CoAP's 6LoWPAN-class footprint optimization (nodes here are ordinary processes, not memory-constrained microcontrollers).

Strengths specific to VMP

  • Loss/duplicate detection across a reconnect (§7), paired with automatic reconnection — MQTT leans on broker-managed QoS levels to get this; CoAP leans on Confirmable messages. VMP gets it without a broker or a transport change.
  • Built-in optional authentication (§8) that costs nothing when unused.
  • A version token that is actually enforced (§9), not just present.
  • Group addressing without a broker (§10) — CoAP has no native equivalent at all; MQTT gets it from infrastructure VMP doesn't need to add.
  • Zero-decoder debuggability — every message is legible straight from the log the assignment already requires.

13. Deferred future work

Considered, and consciously scoped out of this submission as disproportionate to the time available relative to their benefit:

  • Full session resumption — a server-issued session token letting a node resume state after reconnecting instead of REGISTERing from scratch.
  • Message-ID + dedupe — a unique ID per message with server-side dedupe; overlaps substantially with what Seq (§7) already catches.
  • Batch PUSH — multiple readings per message to cut overhead at short intervals; not needed at this project's node counts.
  • TLS — real transport encryption in place of the shared-secret header (§8); deferred over certificate/key setup risk during grading.
